


## 8. Контракты взаимодействия

В контуре системы присутствуют две внешние интеграции, определенные заданием индустриального партнера и схемой `diagrams/landscape.puml`. Ниже приведены спецификации двух контрактов межсервисного взаимодействия.

| Внешняя система | Роль в кейсе | Контракт и протокол |
|-----------------|--------------|---------------------|
| «1С:Университет ПРОФ» | Источник структуры подразделений, аудиторий, преподавателей и первичного расписания кафедр | КНТ-1, REST GET, Basic Auth |
| «Мессенджер MAX» | Канал оперативного информирования студентов и преподавателей через чат-бота | КНТ-2, REST POST, Bearer Token |

### КНТ-1. Загрузка данных расписания и структуры из 1С

**Требование.** Сервер расписания должен по расписанию или по команде диспетчера запрашивать данные подразделений и занятий из публикации HTTP-сервисов «1С:Университет ПРОФ» через метод GET и получать корректный JSON-ответ без модификации данных на стороне 1С.

| Поле | Содержание |
|------|------------|
| Поставщик | ИС «1С:Университет ПРОФ» (публикация HTTP-сервисов `/hs/...`) |
| Потребитель | Сервер «Расписание занятий» (модуль импорта) |
| Протокол | REST, HTTP 1.1, JSON, кодировка UTF-8 |
| Операция | `GET /university_volgmu/hs/volgmed_data/Department_University` |
| Связанные требования | ФТ-1.1, ФТ-1.2, ФТ-1.3, ФТ-1.4, НФТ-4, НФТ-5, НФТ-6 |
| Предусловие | Сетевой шлюз 1С опубликован, учетная запись `SiteAPI` активна и имеет права на чтение справочников |
| Постусловие успеха | Сервер расписания получил тело ответа, отсек возможный текстовый префикс, разобрал JSON и обновил расписание в локальной БД |
| Постусловие отказа | Данные в локальной БД не повреждены, система сохраняет предыдущую версию расписания, ошибка записана в журнал аудита |
| Последовательность | `diagrams/sequence-1c.puml` |

#### Запрос
Тело запроса отсутствует. Параметры авторизации передаются в HTTP-заголовке.

| Поле | Место в сообщении | Тип | Обязательность | Смысл в кейсе | Правило |
|------|-------------------|-----|----------------|---------------|---------|
| `Authorization` | Заголовок HTTP | Строка | Да | Авторизация шлюза | Значение `Basic <base64(SiteAPI:password)>` |
| `Accept` | Заголовок HTTP | Строка | Да | Ожидаемый формат | Значение `application/json, text/plain, */*` |

Пример HTTP-запроса:
```http
GET /university_volgmu/hs/volgmed_data/Department_University HTTP/1.1
Host: 10.128.240.232
Authorization: Basic U2l0ZUFQSToxMjM0NTY=
Accept: application/json
```

#### Ответ
Успешный ответ имеет статус HTTP 200 OK. Перед открывающей скобкой `{` допускается текстовый префикс, который парсер сервиса отсекает перед разбором.

| Поле | Место в сообщении | Тип | Обязательность | Смысл в кейсе | Правило |
|------|-------------------|-----|----------------|---------------|---------|
| `TypeID` | Тело JSON | Строка | Нет | Идентификатор типа сущности | Строковый код типа |
| `GUID` | Тело JSON | UUID-строка | Да | Уникальный идентификатор подразделения/аудитории | Формат UUID 1C |
| `Представление` | Тело JSON | Строка | Да | Название кафедры или аудитории | Не пустое строковое значение |
| `ВидСтруктуры` | Тело JSON | Строка | Да | Категория подразделения | Значения: `Кафедры`, `Аудитории`, `Факультеты` |
| `Характеристики` | Тело JSON | Массив объектов | Да | Параметры аудитории или кафедры | Содержит пары ключ-значение (адрес, количество мест) |
| `Подчиненные` | Тело JSON | Массив узлов | Да | Дерево дочерних подразделений | Рекурсивный массив узлов аналогичной структуры |

Пример успешного JSON-ответа от 1С:
```json
{
  "TypeID": "dep-01",
  "GUID": "a1b2c3d4-e5f6-7a8b-9c0d-1e2f3a4b5c6d",
  "Представление": "Кафедра общей хирургии",
  "ВидСтруктуры": "Кафедры",
  "Характеристики": [
    {
      "Сокращенное наименование": "Каф. общей хирургии",
      "Базирующееся подразделение": "Корпус 1"
    }
  ],
  "Подчиненные": []
}
```

Пример ответа с ошибкой 1С:
```json
{
  "error": true,
  "message": "База данных 1С временно заблокирована для обслуживания",
  "error_text": "Error code 105: Service in maintenance mode"
}
```

#### Исходы

| Исход | Как выглядит в протоколе | Что это значит в кейсе | Что делает вызывающая сторона (сервер расписания) |
|-------|--------------------------|------------------------|---------------------------------------------------|
| Успех | HTTP 200 OK, валидный JSON в теле | Данные структуры и расписания успешно получены | Отрезает текстовый префикс, валидирует схему, удаляет дубликаты и сохраняет данные в локальную БД |
| Ошибка прав доступа | HTTP 401 Unauthorized или 403 Forbidden | Изменился пароль или заблокирована учетная запись SiteAPI | Прекращает операцию, сохраняет старое расписание, отправляет уведомление диспетчеру и пишет ошибку в журнал |
| Ошибка структуры тела | HTTP 200 OK с полем `"error": true` либо битый JSON | 1С вернула системную ошибку вместо расписания | Прекращает разбор тела, данные в БД не обновляет, фиксирует текст ошибки в аудите |
| Недоступность сервера 1С | HTTP 5xx, таймаут ожидания соединения (> 1800 с) или обрыв сети | Сервер 1С отключен, перегружен или недоступен по сети | Прекращает ожидание, продолжает работу на основе локальной базы PostgreSQL, фиксирует инцидент в журнале |

#### Приемка

```text
Given: публикация 1С доступна по сети и учетная запись SiteAPI активна
When: сервер расписания выполняет GET-запрос к эндпоинту Department_University
Then: возвращается HTTP-код 200, в теле содержится валидный JSON, дерево кафедр и аудиторий успешно обновляется в локальной базе данных
```

```text
Given: сервер 1С возвращает HTTP 401 или тело с флагом error: true
When: сервер расписания выполняет попытку синхронизации данных
Then: локальная база расписания остается в прежнем неизменном состоянии, а в журнал аудита записывается сообщение о сбое шлюза 1С
```

Последовательность взаимодействия: `diagrams/sequence-1c.puml`.


### КНТ-2. Отправка уведомлений об изменении расписания в мессенджер MAX

**Требование.** Сервер расписания должен при подтверждении диспетчером изменений в занятии передавать сформированные push-уведомления через HTTP REST POST к Bot API мессенджера MAX для каждого подписанного студента и преподавателя.

| Поле | Содержание |
|------|------------|
| Поставщик | Мессенджер «MAX» (сервис Bot API) |
| Потребитель | Сервер «Расписание занятий» (модуль оповещений) |
| Протокол | REST, HTTPS, JSON, кодировка UTF-8 |
| Операция | `POST /bot/v1/messages/send` |
| Связанные требования | ФТ-7.1, ФТ-7.2, ФТ-8.1, ФТ-8.2, НФТ-6, НФТ-8, НФТ-9 |
| Предусловие | Изменение занятия опубликовано диспетчером; в базе данных есть список активных подписок с известными идентификаторами чатов MAX |
| Постусловие успеха | Сообщение принято сервисом MAX к доставке; сервер расписания получил уникальный идентификатор сообщения `message_id` |
| Постусловие отказа | Сообщение не доставлено; при временном сбое выполняется повторная отправка (до 3 раз), при блокировке бота подписка деактивируется |
| Последовательность | `diagrams/sequence-max.puml` |

#### Запрос
Запрос передается методом POST в формате JSON. Токен доступа передается в заголовке `Authorization`.

| Поле | Место в сообщении | Тип | Обязательность | Смысл в кейсе | Правило |
|------|-------------------|-----|----------------|---------------|---------|
| `Authorization` | Заголовок HTTP | Строка | Да | Токен авторизации бота | Формат `Bearer <bot_api_token>` |
| `Content-Type` | Заголовок HTTP | Строка | Да | Тип содержимого | Значение `application/json` |
| `recipient_id` | Тело JSON | Строка | Да | Идентификатор чата подписчика в MAX | Соответствует сохраненному `chat_id` пользователя |
| `notification_type` | Тело JSON | Строка | Да | Тип оповещения | Значения: `schedule_change`, `class_cancel`, `room_change` |
| `text` | Тело JSON | Строка | Да | Текст уведомления | Понятный текст для пользователя с датой, временем, предметом и аудиторией |

Пример JSON-запроса:
```http
POST /bot/v1/messages/send HTTP/1.1
Host: api.max-messenger.ru
Authorization: Bearer sec_tok_998124_bot
Content-Type: application/json

{
  "recipient_id": "max_user_449102",
  "notification_type": "schedule_change",
  "text": "Внимание! Изменение в расписании на 22.11.2026: пара по Хирургии перенесена на 11:30 в ауд. 302."
}
```

#### Ответ
При успешном приеме запроса шлюз MAX возвращает HTTP 200 OK.

| Поле | Место в сообщении | Тип | Обязательность | Смысл в кейсе | Правило |
|------|-------------------|-----|----------------|---------------|---------|
| `status` | Тело JSON | Строка | Да | Статус обработки шлюзом | Значение `"sent"` или `"queued"` |
| `message_id` | Тело JSON | Строка | Да | Идентификатор сообщения в MAX | Уникальный номер отправленного сообщения |
| `timestamp` | Тело JSON | Строка | Да | Время фиксации шлюзом | Стандарт ISO 8601 / RFC 3339 |

Пример успешного JSON-ответа:
```json
{
  "status": "sent",
  "message_id": "msg_994817204",
  "timestamp": "2026-11-21T12:00:05Z"
}
```

Пример ответа при блокировке бота пользователем:
```json
{
  "status": "error",
  "error_code": 403,
  "message": "User blocked the bot"
}
```

#### Исходы

| Исход | Как выглядит в протоколе | Что это значит в кейсе | Что делает вызывающая сторона (сервер расписания) |
|-------|--------------------------|------------------------|---------------------------------------------------|
| Успех | HTTP 200 OK, `status: "sent"` или `"queued"` | Сообщение принято к доставке получателю в MAX | Фиксирует успешную доставку в журнале и сохраняет `message_id` |
| Пользователь заблокировал бота | HTTP 403 Forbidden, `error_code: 403` | Студент или преподаватель остановил чат-бота в MAX | Помечает подписку пользователя как неактивную, исключая повторные отправки |
| Неверный формат запроса | HTTP 400 Bad Request, описание ошибки валидации | Ошибка в теле запроса (пустой текст или некорректный ID) | Записывает критическую ошибку формирования запроса в лог, повтор не выполняет |
| Сбой сервиса MAX или таймаут | HTTP 500, 502, 503, 504 либо таймаут запроса (> 5 с) | Сервер MAX перегружен или временно недоступен | Помещает сообщение в очередь повторной отправки (до 3 попыток с интервалом в 10 секунд) |

#### Приемка

```text
Given: активная подписка студента на группу с валидным chat_id max_user_449102
When: диспетчер нажимает кнопку «Опубликовать изменения» по перенесенной паре
Then: сервер расписания вызывает POST /bot/v1/messages/send, получает HTTP 200 с message_id, а уведомление отображается в диалоге MAX не позже чем через 30 секунд
```

```text
Given: получатель заблокировал бота в мессенджере MAX
When: сервер расписания отправляет уведомление по данному recipient_id
Then: возвращается HTTP 403 Forbidden, сервер расписания переводит подписку пользователя в неактивный статус и не выполняет повторных вызовов
```

Последовательность взаимодействия: `diagrams/sequence-max.puml`.
