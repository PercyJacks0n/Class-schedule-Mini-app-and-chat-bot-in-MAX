## 2. Спецификация функций

### ФТ-1.1
- Формулировка: Система должна отправлять служебные HTTP GET-запросы к сервисам 1С по расписанию и принимать JSON-выгрузки справочников и пар.
- История-источник: EP-1
- Актор: Подсистема Коннектор, сервер 1С
- Вход: URL сервисов 1С, служебный логин и пароль
- Результат: полученный массив данных в формате JSON
- Ошибочный вход: сервер 1С не отвечает в течение таймаута (1800 с для тяжелых данных, 600 с для легких). Сеанс обрывается, старая база остается рабочей.
- Приоритет MoSCoW: Must have
- Обоснование приоритета: Без получения данных из 1С система не имеет расписания, ручной ввод в проекте не предусмотрен.

```text
Given: наступило время синхронизации по таймеру
When: коннектор отправляет GET-запрос к сервисам 1С
Then: получен ответ со справочниками и расписанием в формате JSON
```

Тип: EQ, сложность низкая (1 внешний файл 1С, 4 поля). Точки: 3.  
Покер: 5, 8, 5, итог 5 поинтов. Раздувает ожидание сетевого ответа и длинные таймауты.

### ФТ-1.2
- Формулировка: Система должна очищать полученный ответ 1С от служебного префикса до первого символа `{` или `[` и проверять корректность структуры JSON.
- История-источник: EP-1
- Актор: Подсистема Коннектор
- Вход: сырой текст ответа 1С
- Результат: валидный объект JSON, готовый к обработке
- Ошибочный вход: в тексте нет валидного JSON или пришел флаг `error: true`. Пакет отбрасывается, администратор получает оповещение.
- Приоритет MoSCoW: Must have
- Обоснование приоритета: 1С может отдавать служебные заголовки перед данными, без их отсечения парсер упадет с ошибкой.

```text
Given: получен сырой ответ от сервера 1С с префиксом
When: коннектор ищет первый символ { или [ и парсит тело
Then: сформирован валидный объект JSON без мусорного заголовка
```

Тип: EI, сложность низкая (1 внешний файл, 4 поля). Точки: 3.  
Покер: 2, 3, 3, итог 3 поинта. Раздувает необходимость обрабатывать объем файла до 2 ГБ в памяти до 400 МБ.

### ФТ-1.3
- Формулировка: Система должна находить и удалять дубликаты записей занятий от разных кафедр при совпадении дня недели, времени, аудитории и группы.
- История-источник: EP-1
- Актор: Подсистема Коннектор
- Вход: распарсенный массив занятий из 1С
- Результат: единый массив занятий без повторяющихся строк
- Ошибочный вход: поврежденная запись без дня или времени. Такая запись пропускается и пишется в журнал ошибок.
- Приоритет MoSCoW: Must have
- Обоснование приоритета: Разные службы вуза дублируют одни и те же пары в 1С, без очистки студенты увидят задвоенные занятия.

```text
Given: в массиве есть две одинаковые пары для одной группы от разных кафедр
When: коннектор выполняет проверку по ключу день-время-аудитория-группа
Then: в итоговом наборе сохраняется только одна чистая запись
```

Тип: EI, сложность средняя (2 файла: чтение 1С и сравнение с базой, 6 полей). Точки: 4.  
Покер: 5, 8, 5, итог 5 поинтов. Раздувает попарное сопоставление большого числа пар между собой.

#### Референс метода на ФТ-1.3

Ниже показан подробный расчет функциональных точек по шагам метода IFPUG на примере функции ФТ-1.3 (очистка от дубликатов). Остальные функции оценены по той же методике.

**Шаг 1. Элементарный процесс.**  
Процесс представляет собой законченную операцию очистки входящего пакета пар перед записью в постоянную базу. Для пользователя это единое действие: получить чистые данные без дублей.

**Шаг 2. Тип транзакции.**  
Процесс принимает входной массив, обрабатывает его и подготавливает для сохранения во внутреннюю базу. Это внешний вход (EI).

**Шаг 3. Число групп данных (FTR).**  
Процесс обращается к 2 группам данных:
1. Внешний файл 1С (EIF) - откуда читаются сырые пары.
2. База расписания (ILF) - куда сохраняются очищенные пары.  
FTR = 2.

**Шаг 4. Число полей (DET).**  
Пользовательские поля, участвующие в проверке дубликатов:
1. День недели
2. Временной слот (номер пары)
3. Номер аудитории
4. Учебная группа
5. ФИО преподавателя
6. Сообщение об ошибке обработки (N_сообщение = 1)  
DET = 5 + 1 = 6.

**Шаг 5. Определение сложности по матрице IFPUG для EI.**  
Матрица сложности для внешнего входа (EI):

| FTR | DET 1-4 | DET 5-15 | DET 16+ |
|---|---|---|---|
| 0-1 | низкая | низкая | средняя |
| **2** | низкая | **средняя** | высокая |
| 3+ | средняя | высокая | высокая |

При FTR = 2 и DET = 6 процесс попадает в клетку «средняя сложность».

**Шаг 6. Вес в точках.**  
Для типа EI средняя сложность дает **4 функциональные точки**.

**Шаг 7. Что в эти точки не входит.**  
Точки самих групп данных (7 точек за базу расписания и 5 точек за 1С) посчитаны в таблице данных в начале документа. К транзакции ФТ-1.3 они повторно не прибавляются. Итоговый вклад ФТ-1.3 равен 4 точкам.

### ФТ-1.4
- Формулировка: Система должна сохранять очищенное расписание и справочники в локальную базу данных микросервиса.
- История-источник: EP-1
- Актор: Подсистема Коннектор
- Вход: проверенный массив расписания
- Результат: обновленные таблицы расписания в базе микросервиса
- Ошибочный вход: сбой записи в базу или разрыв соединения. Транзакция откатывается, в базе остается прошлая рабочая копия.
- Приоритет MoSCoW: Must have
- Обоснование приоритета: Без сохранения расписания в своей базе бот и Mini App не смогут работать при недоступности 1С.

```text
Given: массив расписания очищен от дублей
When: коннектор записывает данные в локальную базу
Then: таблицы расписания обновлены, прошлая версия заархивирована
```

Тип: EI, сложность низкая (1 файл расписания, 8 полей). Точки: 3.  
Покер: 3, 5, 3, итог 3 поинта. Раздувает управление транзакцией с возможностью отката.

### ФТ-2.1
- Формулировка: Система должна автоматически записывать в журнал аудита дату, время, инициатора, тип операции и статус для каждого действия (импорт, выгрузка, экспорт, сбой).
- История-источник: EP-2
- Актор: Микросервис расписания
- Вход: параметры события (время, логин сотрудника или CRON, код операции, статус)
- Результат: новая строка в журнале аудита
- Ошибочный вход: база журнала недоступна. Выполнение операции блокируется с уведомлением администратора.
- Приоритет MoSCoW: Must have
- Обоснование приоритета: Требование BREQ-5 требует 100% фиксации действий сотрудников для расследования инцидентов.

```text
Given: завершилась операция импорта или экспорта
When: микросервис перехватывает событие завершения
Then: в таблице аудита сохранена запись с временем, автором и результатом
```

Тип: EI, сложность низкая (1 файл журнала, 5 полей). Точки: 3.  
Покер: 2, 2, 3, итог 2 поинта. Простая запись одной строки в таблицу логов.

### ФТ-2.2
- Формулировка: Система должна отображать записи журнала аудита с возможностью фильтрации по датам, типу действия и статусу.
- История-источник: EP-2
- Актор: Сотрудник Учебного управления, администратор
- Вход: параметры фильтра (диапазон дат, тип действия, статус)
- Результат: таблица событий аудита на экране
- Ошибочный вход: неверный формат даты. Выводится подсказка, фильтр сбрасывается на текущий день.
- Приоритет MoSCoW: Should have
- Обоснование приоритета: Фильтры нужны для удобства поиска записей, но базовое сохранение логов важнее.

```text
Given: сотрудник открыл раздел журнала аудита
When: он задает фильтр по типу операции «Импорт»
Then: на экране показан список сеансов импорта с их статусами
```

Тип: EQ, сложность низкая (1 файл журнала, 6 полей). Точки: 3.  
Покер: 2, 3, 3, итог 3 поинта. Стандартная экранная таблица с фильтрами и постраничным выводом.

### ФТ-3.1
- Формулировка: Система должна проверять отсутствие у одного преподавателя двух и более назначенных занятий в один и тот же временной слот (правило BR-1).
- История-источник: EP-3
- Актор: Подсистема Коннектор
- Вход: массив импортированных пар
- Результат: признак проверки занятости преподавателей
- Ошибочный вход: в записи не указан преподаватель. Проверка пропускается, занятие помечается как требующее уточнения.
- Приоритет MoSCoW: Must have
- Обоснование приоритета: Преподаватель физически не может вести две разные пары одновременно.

```text
Given: в сетке у преподавателя назначены две пары на одно время
When: система запускает сверку по правилу BR-1
Then: найдено пересечение, пара отправляется на маркировку ошибки
```

Тип: EQ, сложность низкая (1 файл расписания, 4 поля). Точки: 3.  
Покер: 3, 3, 5, итог 3 поинта. Простой поиск одинакового времени у одного человека.

### ФТ-3.2
- Формулировка: Система должна проверять отсутствие двух и более учебных групп в одной аудитории в одно время (правило BR-2) с исключением для потоковых лекций.
- История-источник: EP-3
- Актор: Подсистема Коннектор
- Вход: массив пар с номерами аудиторий и группами
- Результат: список коллизий помещений
- Ошибочный вход: нет номера аудитории (дистанционная пара). Проверка физического помещения не проводится.
- Приоритет MoSCoW: Must have
- Обоснование приоритета: Без проверки аудиторий группы придут на занятия в один кабинет.

```text
Given: в одной аудитории стоят две группы на один час
When: система видит, что преподаватель и предмет разные (не поток)
Then: фиксируется нарушение правила BR-2
```

Тип: EQ, сложность средняя (1 файл расписания, 6 полей, логика исключений для потоков). Точки: 4.  
Покер: 5, 5, 8, итог 5 поинтов. Раздувает проверка условий объединения в лекционный поток.

### ФТ-3.3
- Формулировка: Система должна присваивать статус «Конфликт» спорным парам с сохранением причин накладки для аналитического отчета.
- История-источник: EP-3
- Актор: Подсистема Коннектор
- Вход: найденные пересечения по BR-1 и BR-2
- Результат: проставленный флаг конфликта в базе у конкретных занятий
- Ошибочный вход: сбой записи флага в базу. Занятие не допускается к публикации.
- Приоритет MoSCoW: Must have
- Обоснование приоритета: Спорные пары нельзя скрывать или молча публиковать, их нужно маркировать для диспетчера.

```text
Given: обнаружена коллизия по аудитории
When: система завершает проверку правил
Then: записи получают статус Конфликт с текстом «Пересечение групп 211 и 212»
```

Тип: EI, сложность низкая (1 файл расписания, 5 полей). Точки: 3.  
Покер: 2, 3, 2, итог 2 поинта. Простое выставление булевого флага и строки ошибки.

### ФТ-4.1
- Формулировка: Система должна рассчитывать процент занятости каждой физической аудитории за выбранный семестр или диапазон дат на основе импортированного расписания.

- История-источник: EP-4

- Актор: Сотрудник Учебного управления, микросервис расписания

- Вход: диапазон дат, учебный корпус или факультет

- Результат: сводная таблица с коэффициентом утилизации (%) по каждой аудитории

- Ошибочный вход: за выбранный период в базе отсутствуют записи расписания. Расчёт прерывается, выводится предупреждение о необходимости выполнить импорт данных.

- Приоритет MoSCoW: Should have

- Обоснование приоритета: Необходимо Учебному управлению для выявления простоев и перегруза помещений, но не блокирует запуск просмотра расписания студентами в первый день семестра.

```text
Given: сотрудник Учебного управления выбрал корпус и диапазон дат
When: микросервис агрегирует занятые слоты пар по каждой аудитории и делит на общий фонд времени
Then: на экране отображается таблица с процентом занятости аудиторий
```
Тип: EO, сложность низкая (1 файл расписания с вычислением процента, 5 полей). Точки: 4.

Покер: 3, 5, 5, итог 5 поинтов. Раздувает логика подсчёта общего доступного фонда времени с учётом выходных и сменности.

### ФТ-4.2
- Формулировка: Система должна суммировать академические часы нагрузки по каждому преподавателю из расписания и сопоставлять их со штатной ставкой из справочников 1С.

- История-источник: EP-4

- Актор: Сотрудник Учебного управления, микросервис расписания

- Вход: семестр, кафедра, данные расписания и штатные ставки сотрудников из справочника 1С

- Результат: отчёт по нагрузке преподавателей с индикацией перегруза или недобора часов

- Ошибочный вход: в справочнике 1С отсутствует ставка сотрудника. Часы выводятся без процента выполнения ставки с пометкой «Ставка не указана».

- Приоритет MoSCoW: Should have

- Обоснование приоритета: Позволяет контролировать выполнение учебных планов и распределение нагрузки на кафедрах.

```text
Given: в базе сохранено расписание и актуальный справочник сотрудников из 1С
When: сотрудник запрашивает отчёт по кафедре за семестр
Then: система суммирует часы занятий каждого преподавателя и сравнивает со ставкой
```

Тип: EO, сложность средняя (2 файла: база расписания и справочники 1С, 7 полей с расчётом отклонения). Точки: 5.

Покер: 5, 5, 5, итог 5 поинтов. Раздувает объединение данных из двух источников и корректный учёт потоковых лекций (чтобы часы не задваивались).

### ФТ-4.3
- Формулировка: Система должна формировать и отображать в аналитическом отчёте перечень зафиксированных при импорте конфликтов и накладок (правила BR-1 и BR-2) с группировкой по кафедрам.

- История-источник: EP-4

- Актор: Сотрудник Учебного управления

- Вход: фильтр по подразделению или периоду

- Результат: список спорных занятий с указанием аудитории, времени, конфликтующих групп или преподавателя

- Ошибочный вход: конфликтов не найдено. Выводится статус «Коллизий не обнаружено».

- Приоритет MoSCoW: Should have

- Обоснование приоритета: Даёт диспетчеру готовый список накладок для точечного исправления в 1С.

```text
Given: при импорте часть пар получила статус «Конфликт»
When: сотрудник открывает сводку конфликтов по кафедрам
Then: система выводит список всех пересечений с причинами накладки
```
Тип: EQ, сложность низкая (1 файл расписания с фильтрацией по флагу конфликта, 6 полей). Точки: 3.

Покер: 3, 3, 3, итог 3 поинта. Обычная выборка помеченных записей из локальной базы.

### ФТ-5.1

- История-источник: EP-5
- Актор: Веб-сервис Mini App, студент, преподаватель
- Вход: токен авторизации, тип фильтра (группа/преподаватель/аудитория) и его значение
- Результат: JSON-массив занятий на 6 дней недели
- Ошибочный вход: неверный токен доступа или группа не найдена. Возвращается понятный код ошибки 404 или 401.
- Приоритет MoSCoW: Must have
- Обоснование приоритета: Основной интерфейс Mini App работает через этот API, без него сервис пуст.

```text
Given: Mini App запрашивает расписание группы ИВТ-31
When: микросервис получает корректный токен и номер группы

```

### ФТ-5.2

- Актор: Студент, преподаватель

### ФТ-6.2

### ФТ-7.1

- Ошибочный вход: в базе нет записей для выбранного подразделения или не хватает места на диске. Генерация отменяется, выводится сообщение об ошибке.

Тип: EO, сложность средняя (2 файла: база расписания и справочники 1С, 9 полей с преобразованием в табличный документ). Точки: 5.

Покер: 8, 8, 5, итог 8 поинтов. Раздувает строгое соответствие форматам дат, типов пар и колонок шаблона загрузки MAX.
