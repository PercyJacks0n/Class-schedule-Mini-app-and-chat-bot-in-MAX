## 2. Спецификация функций


### ФТ-5.1
- Формулировка: Система должна передавать по API расписание на неделю для выбранной группы, преподавателя или аудитории со временем ответа до 2 секунд.
- История-источник: EP-5
- Актор: Веб-сервис Mini App, студент, преподаватель
- Вход: токен авторизации, тип фильтра (группа/преподаватель/аудитория) и его значение
- Результат: JSON-массив занятий на 6 дней недели
- Ошибочный вход: неверный токен доступа или группа не найдена. Возвращается понятный код ошибки 404 или 401.
- Приоритет MoSCoW: Must have
- Обоснование приоритета: Основной интерфейс Mini App работает через этот API, без него сервис пуст.

```text
Given: Mini App запрашивает расписание группы ИВТ-31
When: микросервис получает корректный токен и номер группы
Then: за 1.2 секунды возвращается массив пар с понедельника по субботу
```

Тип: EQ, сложность низкая (1 файл расписания, 8 полей). Точки: 3.  
Покер: 3, 5, 3, итог 3 поинта. Раздувает обеспечение времени ответа строго до 2 секунд при пиках.


### ФТ-5.2
- Формулировка: Система должна отображать в веб-интерфейсе Mini App интерактивную сетку занятий по дням недели (пн-сб) и слотам пар с выделением типа занятия.
- История-источник: EP-5
- Актор: Студент, преподаватель
- Вход: полученный JSON расписания недели
- Результат: табличная календарная сетка на экране смартфона или ПК
- Ошибочный вход: на выбранный день занятий нет. Отображается пустая плашка «Занятий нет, выходной».
- Приоритет MoSCoW: Must have
- Обоснование приоритета: Главный пользовательский экран системы, реализующий бизнес-цель наглядного просмотра пар.

```text
Given: данные расписания получены от API
When: фронтенд Mini App выполняет отрисовку
Then: пользователь видит таблицу пар с 1 по 8 с цветовыми маркерами лекций и практик
```

Тип: EQ, сложность низкая (1 файл расписания, 7 полей). Точки: 3.  
Покер: 5, 5, 5, итог 5 поинтов. Раздувает адаптивная верстка под экран WebView мессенджера MAX и мобильные браузеры.


### ФТ-5.3
- Формулировка: Система должна показывать список свободных аудиторий в выбранном корпусе на указанную пару путем исключения занятых помещений.
- История-источник: EP-5
- Актор: Студент, преподаватель
- Вход: номер корпуса, день недели, номер пары
- Результат: перечень свободных аудиторий с указанием их вместимости
- Ошибочный вход: все аудитории заняты. Выводится сообщение «Свободных аудиторий нет».
- Приоритет MoSCoW: Should have
- Обоснование приоритета: Полезная функция для поиска мест для самостоятельной работы, но базовое расписание работает и без нее.

```text
Given: пользователь ищет свободный кабинет в корпусе А на 3 пару
When: система берет все аудитории корпуса и вычитает занятые парами
Then: выводится список: ауд. 204, ауд. 310 (свободны)
```

Тип: EO, сложность средняя (2 файла: занятые пары и фонд аудиторий 1С, 6 полей с операцией вычитания списков). Точки: 5.  
Покер: 3, 5, 5, итог 5 поинтов. Раздувает логика сравнения полного списка аудиторий с активным расписанием.




### ФТ-6.1
- Формулировка: Система должна выявлять изменения (дельту) между новой выгрузкой из 1С и сохраненной базой (отмена, перенос времени, смена аудитории или преподавателя).
- История-источник: EP-6
- Актор: Микросервис расписания
- Вход: новая выгрузка и текущая база
- Результат: массив измененных занятий со старыми и новыми значениями
- Ошибочный вход: изменений нет (дельта пуста). Процесс завершается, рассылка уведомлений не начинается.
- Приоритет MoSCoW: Should have
- Обоснование приоритета: Без выявления дельты невозможно точечно уведомить студентов о переносах пар.

```text
Given: в 1С пара перенесена со 2 на 4 пару
When: система сравнивает новую запись со старой в базе
Then: сформировано событие изменения: группа, предмет, перенос времени
```

Тип: EO, сложность низкая (1 файл расписания, 7 полей со сравнением атрибутов). Точки: 4.  
Покер: 5, 8, 8, итог 8 поинтов. Раздувает попарная проверка всех полей каждого занятия при синхронизации.


### ФТ-6.2
- Формулировка: Система должна формировать и отправлять адресные push-уведомления в диалог с ботом пользователям, подписанным на изменившиеся группы или преподавателей, пачками по 100-300 сообщений.
- История-источник: EP-6
- Актор: Микросервис расписания, платформа MAX
- Вход: список изменений и таблица подписок пользователей
- Результат: доставленные сообщения в чаты пользователей мессенджера
- Ошибочный вход: платформа MAX вернула ошибку 429 (превышение лимита). Отправка приостанавливается, сообщения уходят в очередь повтора.
- Приоритет MoSCoW: Should have
- Обоснование приоритета: Позволяет предупредить студентов об отменах, батчинг защищает бота от блокировки за спам.

```text
Given: для группы ИВТ-31 отменилась первая пара
When: микросервис находит 25 студентов этой группы и шлет сообщения в MAX
Then: студенты получают пуш: «Внимание: пара по физике в 9:00 отменена»
```

Тип: EI, сложность средняя (2 файла: расписание и подписки пользователей, 6 полей). Точки: 4.  
Покер: 5, 8, 8, итог 8 поинтов. Раздувает дробление на батчи с паузами для соблюдения лимитов мессенджера MAX.


### ФТ-6.3
- Формулировка: Система должна сохранять неотправленные сообщения в очередь повторной отправки при сбое шлюза MAX с автоматическим удалением сообщений старше 12 часов.
- История-источник: EP-6
- Актор: Микросервис расписания
- Вход: пакет сообщений, не принятый шлюзом MAX
- Результат: сообщения сохранены в буфере повтора; устаревшие удалены
- Ошибочный вход: шлюз не работает больше суток. Сообщения помечаются как просроченные и очищаются.
- Приоритет MoSCoW: Should have
- Обоснование приоритета: Гарантирует доставку при коротких сетевых сбоях и защищает студентов от устаревших вчерашних пушей.

```text
Given: пропала связь с сервером MAX
When: система не смогла доставить уведомление
Then: сообщение помещается в очередь повтора с временем жизни 12 часов
```

Тип: EI, сложность низкая (1 файл очереди, 5 полей). Точки: 3.  
Покер: 3, 5, 5, итог 5 поинтов. Раздувает логика фонового планировщика повторных отправок и проверка срока жизни (TTL).
